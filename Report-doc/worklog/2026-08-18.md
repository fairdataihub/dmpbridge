## 1. pdfplumber pipeline — full replacement, not an extension

Per explicit instruction, replaced pdfplumber's line-by-line extraction +
per-block classification with the approach in
`notebooks/with-pdfplumber-visual-signals.ipynb`: the whole document is read as
one text string, with words visually emphasized relative to the document's own
body-text font wrapped in `**bold**` markers and italics in `_markers_`, then
classified in a single model call that returns `[{"text", "label"}]` directly —
no block ids, no per-block bbox/font metadata, no separate segmentation step.

**Ported name-for-name, not just behavior-for-behavior**, after the first pass
was found to have quietly renamed things (`clean_labeled_output` became
`_clean_visual_signal_output` with an added label-validation check the notebook
never had). Corrected once caught: `dmpbridge/strategies/wholedoc.py` now
defines `classify_entire_document()` and `clean_labeled_output()` with the same
signatures and logic as the notebook, including the notebook's own `print()`
statements rather than swapping in `logger.info()`. The two deliberate,
disclosed departures from the notebook: `model` comes from the strategy's own
configuration instead of being hardcoded to `qwen2.5:14b`, and the HTTP call
goes through this project's existing `OllamaModel` (deterministic,
`temperature=0.0`) rather than the notebook's raw `ollama.chat()`, which had no
temperature set and measurably varied item counts run to run.

**Word-level dedup restored, but relocated.** The old `text_cleaner.py`'s
duplicate-word removal (`"Roles Roles and and"` → `"Roles and"`, from PDFs that
render each word twice in offset layers) was dropped in the first pass, then
explicitly asked for back. Re-added as `_dedup_consecutive_words()` in
`pdfplumber_reader.py`, but running on the raw word list **before** `**`/`_`
markers are inserted, not on the final marked-up text — applying it after
marker insertion would let a bare `**`/`_` token collide with adjacent
punctuation (both normalize to `""`) and get deleted as a false duplicate,
corrupting the marker pairing. Char-level dedup (`_deduplicate_chars`, for
PDFs that render each *character* twice) was not restored — the notebook never
had it, and the known defect it would fix (samples 3, 9) is now a disclosed,
unfixed limitation rather than a silent one.

## 2. Docling and LightOnOCR removed entirely

Two separate, explicit requests — "remove docling" then, in a later message,
"remove lighton too... I can come back when I have an idea about this."

**Docling:** `docling_extractor.py` deleted, `get_extractor()` no longer
recognizes it, its two results notebooks (7, 8) deleted, `pyproject.toml`'s
`docling` extras group removed, and every doc/diagram/script mention updated —
39 files touched in total. Old on-disk output for all three models under
`*_docling_whole_doc/` was deleted at the user's explicit choice ("delete
outright", no archive).

**LightOnOCR**, removed the same way, additionally took the *id-based*
classification path with it — `lighton_extractor.py`, `dmpbridge/prompts/system.py`
(deleted outright), `OUTPUT_SCHEMA`, and `wholedoc.py`'s `_build_payload`/
`_apply_labels` helpers all existed only to serve lighton's per-block-with-ids
approach. Per explicit confirmation this was genuinely dead code once lighton
was gone, not infrastructure to keep for a hypothetical future extractor.
`OllamaModel.complete()` now requires `schema` explicitly instead of falling
back to `OUTPUT_SCHEMA`. `converter.py`'s `_strip_markdown()` also removed as a
second-order consequence — it existed solely to strip markdown headers
LightOnOCR's OCR output produced; pdfplumber never emits them.

**`dmpbridge/prompts/labels.py` renamed to `constants.py`** partway through,
after being asked twice why the project had three (then two) prompt files.
The honest answer, given directly: pdfplumber's `SYSTEM_PROMPT`/`schema`
couldn't share a file with `system.py`'s `SYSTEM_PROMPT` (two module-level
variables, same name, one file — the second definition would silently
overwrite the first), so they ended up in `labels.py` by elimination, not
because the name fit. Renamed once that was pointed out.

`pdfplumber` is now the only extractor in the pipeline. Confirmed after each
removal with a live run, not just a passing test suite.

- Row 3 (`E,E,N,E`): `section.description` → both `question.text` and `section.title`
- Row 9 (`N,E,E,E`): document `title` → both `question.text` and `section.title`

Implemented in `annotation_rules.py`: `_RULES`'s value type changed from a
single `(source, target)` pair to a tuple of pairs, `apply_new_annotation_rules()`
now loops over all actions per row, reading every source from a snapshot taken
before any action in the row runs (so a two-action row can't have its second
action see the first action's output). Corresponding tests updated, including
one new invariant (`test_section_title_is_only_ever_filled_when_blank`) since
the old one (`test_section_title_is_never_written`) is now false by design.

**The actual `data/input/Rules.xlsx` file was never updated** — every write
attempt hit `PermissionError`, meaning it was open (likely in Excel) at the
time. The code-side change is real and live; the spreadsheet itself still
reads the old single-target wording for both rows. Two tests currently fail as
a direct, expected consequence: `test_rules_table_matches_the_spreadsheet`
(code and sheet now disagree) and `test_reproduces_the_new_annotation_for_every_sample`.

**That second failure is the important one.** It applies the current rules to
the *old* ground truth and checks it reproduces the *new* ground truth exactly,
across all 10 real documents. With row 9 also filling `section.title`, it now

sample7: section.title  new=''  →  rule produces  'Resource/Data Sharing Plan'

Raised directly: proceed anyway (meaning the two reference files are what's
arguably out of date), drop the `section.title` half of row 9 specifically, or

## 5. A separate, real defect surfaced by real output: markers not always stripped

While investigating §4's row-9 effect on sample4, found the model had returned
the document title as `'** DATA MANAGEMENT PLAN **'` — the `**` markers were
not stripped, despite the system prompt explicitly instructing exactly that.
This is not new — flagged as a known limitation of the visual-signal approach
earlier in the project — but this is the first time it was caught in a fresh
run under the current (post-§1) pipeline rather than in the original prototype
notebook. Not fixed; recorded so it isn't mistaken for a new regression next
time it's seen.
