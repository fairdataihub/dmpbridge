## 3. The confusion-matrix bug: rows didn't sum to 100%

### The defect

`build_pct()` in `build_comparison_notebook.py` divided by the row total
(predictions + never-produced) to make the diagonal read as recall, but only
ever **drew** the five label columns. The `__missed__` share was in the
denominator and invisible in the picture — so `section.title` for llama3.1:8b
showed 88%, correctly computed, with the missing 12% simply never drawn.

Confirmed the size of what was hidden — up to 43% of a row (`question.text`,
llama3.1:8b, Path B: 24 of 56 real questions never produced anything at all).

### The fix

Added a sixth column, `(not labeled)` (renamed from an initial `(not
produced)` at the user's request), set off with a heavy divider rule since it
is not a label the model chose. A new `verify-100` cell asserts every row now
sums to exactly 100%, computed from the raw confusion dict rather than trusted
by eye.

### Section 4 — which items, not just how many

Added a full accounting: a per-class percentage summary, the actual list of

the clearest number of the day — pooled across all three models at 100%

### The raw-count matrix and a second, related shading bug

## 4. Two different reasons items go unlabeled — verified, not assumed

Prompted by the question "why do all three models miss the *same* items in
Path A?" — checked whether it was really the same items or just a matching
count, by comparing the actual sets.

**Path A, sample 6: genuinely identical**, set-equality confirmed, not just
equal counts. All three models miss the exact same 8 items at 75% overlap.
Cause: stage 1 extraction is keyed by extractor only, not by model, so all
three models read one shared file. An underlined heading in sample 6 arrives
on the same physical line as the start of its answer — pdfplumber output,
before any model runs — so no label choice can separate them; whichever label
wins, the merged block matches the answer's words, not the heading's.
Confirmed this identity breaks down at the 100% threshold (11/13/12 items,
only 10 of 14 shared) — stricter matching starts being sensitive to how each
model's own merges land, so identical counts is a real but narrow signature of
fused blocks, not a general property.

Went one level deeper on the same document: on the parts extraction did
**not** damage, the three models are clearly not the same —
llama3.3:70b gets 6/11 items right on sample 6 overall, gemma4:e4b 3/11,
llama3.1:8b 1/11. "All three models are the same on sample 6" is only true for
the six items extraction pre-decided.

**Path B: differences are model-driven, and the mechanism is a scoring
artifact.** The annotation rule fills a blank `question.text` from the section
title, but only when the model's own field was empty. Traced two items in
sample 2 (`"2. Data used in publications"`, `"4. Confidentiality, security and
rights"`) where llama3.1:8b and llama3.3:70b both wrote a real answer
paragraph into `question.text` — correct behavior — so the rule left it alone,
and it doesn't match the annotation's title-repeat expectation, scoring as
missing. gemma4:e4b left the field blank in both cases, the rule auto-filled
it with the title text, and it matched by coincidence. **The model that
answered less is rewarded; the two that answered more are penalised** — a
side effect of the rule, not a capability difference. Added a live worked
example of this (section 5, both notebooks) that inspects each model's raw
stage-3 JSON and prints the fill state directly, rather than asserting it.

**Then checked whether this generalizes beyond the two documents used as the
example — it does not stay contained.** Path B has 81 missing items pooled
across all three models at 100% overlap, more than double Path A's 36, and
spread across **8 of the 10 documents** rather than 4. Samples 2 and 6 are
still the largest single contributors but are only 57% of the Path B total,
down from being nearly all of Path A's. Not yet added to the notebook — the
section 5 conclusion currently reads as if the effect is contained to the two
example documents, which understates it.

## 1. What existed before today

`docling_extractor.py` and its CLI/pipeline wiring (`--extractor docling`,
`scripts/run_docling.ps1`) already existed, added in an earlier session
(`87ee4d8`) but **never actually run** — no cached extraction, no labeled

was exercised end to end.

## 2. Redesign 1 — markdown export, OCR forced on every page

Rewrote `_document_to_blocks` to parse `doc.export_to_markdown()` per page
instead of walking Docling's item tree, so headings would carry `#`/`##`
literally. Set `force_full_page_ocr=True` — OCR re-reads every page as an
image regardless of whether a text layer exists, chosen deliberately to test
OCR itself rather than only its scanned-page fallback behaviour.

**Two bugs found before this got near Ollama:**

- Splitting the markdown on blank lines alone silently re-fused sample 6's
  five numbered section headings into one paragraph-sized block — Docling's
  markdown serialiser joins a run of list items with single newlines, not
  blank lines, in this specific case. Fixed by splitting each blank-line
  chunk again on single newlines. Verified this doesn't fragment ordinary
  prose: Docling's markdown export never puts an internal single-newline
  break inside a normal wrapped paragraph.
- The first working version's docstring claimed markdown markers were "kept
  verbatim in block text" — they were not; the code stripped `#`/`##`/`- `
  and stored only a same-shape `is_bold` boolean, functionally identical to
  the pre-existing extractor it was meant to replace. Caught by the user
  asking "why the output in docling it's not markdown", not by inspection.
  Fixed to keep the literal marker in `text`.

First full run, this version: `llama3.1:8b` + `docling`, all 10 samples,
107.5 s. First results notebook (`7-llama31-8b-results-docling.ipynb`,
now deleted): **Path A f1 0.358, Path B f1 0.344** — against the pdfplumber
baseline for the same model, same 100%-overlap threshold, of **0.287 / 0.313**.
Code for this version: commit `4be4796`.

## 3. Redesign 2 — item-tree walk + regex run-in-heading splitter

Two external scripts were shared for comparison (not committed to this repo):
a section-level Docling extraction script with a `RUN_IN_HEADING` regex, and
a simpler `test_docling.py` that groups everything between headings into one
block per section. Evaluated both rather than adopting either:

- The whole-section-blob approach (`test_docling.py`'s `split_into_sections`)
  was rejected outright — it would merge `section.description`,
  `question.text`, and `answer.text` into one block per section, which this
  pipeline cannot label correctly by construction (one block gets one
  label). Right tool for chunking a paper for retrieval, wrong one for
  field-level classification.
- The `RUN_IN_HEADING` regex idea was real: tested against every block
  already extracted across all 10 documents and found it split sample 6's 5
  fused headings correctly with zero false positives elsewhere — but it
  requires a numbered/lettered prefix (`"1. "`, `"B. "`) in the text, and
  sample 2's actual fused heading (`"Roles & Responsibilities. For the
  proposed research..."`) has none, so it didn't catch that case.

Rewrote the extractor a second time to walk `doc.iterate_items()` directly
(not the flattened markdown string), which recovered per-block bbox/page
provenance that redesign 1 had silently dropped, and added a `section` field
to every block. Layered three regex patterns on top for run-in headings: a
standalone-numbered pattern, a numbered-run-in pattern, and a new
bare-phrase pattern (Title-Case, 2+ words, no number) to close the sample-2
gap the external script's regex missed.

**First version of the bare-phrase pattern had a real bug, caught only by
testing against the actual item text Docling produces, not assumed text:**
`LIST_ITEM`-labelled elements do not include their own `"1."`/`"2."` marker in
`item.text` — Docling's markdown renderer re-adds it separately — so the
numbered pattern could never match them at all. Separately, these particular
headings (`"Types of data"`, `"Policies for access and sharing"`) turned out
to be plain sentence case, not Title Case, so the bare-phrase pattern didn't
catch them either. **The fix that was supposed to solve sample 6 did not
touch sample 6.** Found by re-extracting and inspecting real block output,
not by re-reading the regex. Fixed with a fourth, looser pattern scoped
specifically to `LIST_ITEM`-labelled text, relying on Docling's own
structural label as the extra evidence needed to justify dropping the
capitalisation requirement. Re-tested against all 10 documents: 5/5 known
cases split, 0 false positives on the other 15 list items in the corpus.

Not run through Ollama at this stage — validated by direct extraction only.

## 4. The overfitting check, and what it found

Asked directly whether this was "specialized for one or two samples with
some rules." Checked, rather than reassured: **yes, partially.** Of 8
connector words written into the bare-phrase pattern (`&`, `and`, `of`,
`for`, `in`, `to`, `the`, `or`), 6 were added speculatively, guessing they'd
help future documents — not one was exercised by any real example in this
corpus, and none had been checked for false-positive risk. That is the same
failure mode as hardcoding to two samples, just wearing a more
general-looking disguise. Removed the 6 untested ones; re-verified the
trimmed pattern gives identical block/heading counts across all 10 documents
(expected, since the removed branches were never firing on this corpus
anyway).

**The deeper point, stated plainly rather than resolved:** even after that
fix, every false-positive check for every pattern was run against the same
10-document corpus the patterns were designed against. That is evidence the
rules don't break anything currently on disk — it is not evidence they
generalise to a DMP nobody has looked at yet. No held-out document existed
today to actually test that.

## 5. Redesign 3 — regex removed entirely, per explicit instruction

User: *"i do not want regex patterns."* Removed all four patterns, keeping
the item-tree walk, bbox/page recovery, `section` field, table-to-markdown
support, and forced OCR. Heading detection is now Docling's own layout
model alone (`TITLE`/`SECTION_HEADER` labels) — nothing hand-written on top.
Documented consequence in the module docstring rather than silently
absorbing it: a heading typed on the same line as its own paragraph (sample
6; part of sample 2) stays one block, one label, un-split. Verified across
all 10 documents: no crashes, sample 6 back to 6 blocks (the 5 numbered items
fused again, as expected). Code for this version: `456ced9`.

Cleared the stale cache and re-ran end to end:

| model | Path A f1 | Path B f1 | vs. pdfplumber (100% overlap) |
|---|---|---|---|
| `llama3.1:8b` | 0.359 | 0.339 | 0.287 / 0.313 |
| `gemma4:e4b` | 0.438 | 0.415 | 0.656 / 0.665 |

**Contradicted the expectation going in.** Removing the regex fix — which
had demonstrably repaired sample 6's fused headings — moved the pooled
`llama3.1:8b` score by **less than 0.001** (0.358 → 0.359). Checked why
rather than accepting the coincidence: sample 6 alone dropped to 1/11 items
correct (a real, large regression for that one document), but it is only 11
of 132 items pooled across all 10 documents, so an 8%-of-corpus document's
damage barely moves a pooled micro-average. The aggregate number is not a
reliable signal for whether a single-document fix mattered.

**Also contradicted the working hypothesis about Docling generally.**
`gemma4:e4b` + docling scored 0.438 / 0.415 — clearly *behind* its
pdfplumber baseline of 0.656 / 0.665, not ahead of it, despite `llama3.1:8b`
improving on docling relative to its own pdfplumber baseline. Whatever is
producing `llama3.1:8b`'s improvement over pdfplumber is not a general
"Docling is better" effect — it did not hold for the second model tested,
and nothing today identified the actual cause. Left open, not resolved.

`llama3.3:70b` was never run on docling — the ~20-minute job was not reached
before the revert decision.

## 6. What OCR actually contributed, checked directly

Compared the same real sentence read by pdfplumber (text-layer) and Docling
(forced OCR, RapidOCR engine, GPU) on sample 1: pdfplumber read `"(iii)
NHANES cohorts"` correctly; Docling's OCR misread it as `"(ili) NHANES
cohorts"`. A genuine OCR error introduced on text pdfplumber already had
right. **None of the current 10 sample documents are scanned or have a
broken text layer**, so OCR's actual justification (recovering text from
pages with no usable text layer) was never exercised by this test set —
today's numbers reflect OCR's downside (occasional misreads) with none of
its upside demonstrated. That is a fact to tell the advisor plainly: Docling
was tested, OCR was on, but the OCR-specific benefit remains unverified on
documents we actually have.
