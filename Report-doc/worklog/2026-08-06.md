## 1. Annotation rules — the column-order incident

The rules were rewritten three times today as `Rules.xlsx` was revised. The middle
revision cost the most time and is the one worth remembering.

### What happened

The sheet's column order changed from

```
# | title | question.text | section.title | section.description | Action
```

to

```
# | title | section.title | section.description | question.text | Action
```

`question.text` moved from column 2 to column 4. **The action text did not change**, so
nothing looked obviously broken — but the transcription was still keyed on the old order,
which silently remapped every row.

Under the misread order six of sixteen rows became incoherent: they named a source field
the same row marked empty, or wrote into a field the row marked as already populated. I
reported this at the time as "the sheet contradicts itself" and quantified the damage as
32 no-ops and 9 overwrites. **That analysis described the misread table, not the intent.**

### Impact and resolution

| Column order | Agreement with reference files |
|---|---|
| `question.text` in column 2 (misread) | 2/10 |
| **`question.text` in column 4 (correct)** | **10/10** |

With the correct order the table is entirely coherent and expresses one rule:

- **`question.text` already has text** → leave alone *(every even row)*
- **`question.text` is empty** → fill from the first available source:
  `section.title` → `section.description` → document title

### Safeguards added

- `RULE_FIELDS` in `annotation_rules.py` records the expected column order.
- `test_rules_table_matches_the_spreadsheet` **reads the sheet header at test time** and
  fails if it does not match `RULE_FIELDS`. Verified by tampering with a row in code and
  confirming it was caught.
- The same assertion runs in `annotation_conversion_test.ipynb`, which also contains a
  cell reproducing the failure (10/10 vs 2/10) so the mechanism stays visible.

### Sample 5 is no longer a special case

Earlier work recorded sample 5 as needing several sub-questions merged into one with
answers concatenated, and treated that as underivable from the JSON alone. Under the
current table it matches exactly. **No merging is required** — that open problem is closed.

## 2. Prompt bug — lettered sub-items

### Diagnosis

Looking at sample 1's stage-3 output against the old annotation, both models made the same
mistake: `question.text` → `section.title`, on items like `"B. Scientific data that will
be preserved…"`. It was the single largest error class for both — 12 occurrences for
llama3.1:8b, 10 for gemma4:e4b.

The cause was in the prompt. What the gold data actually uses:

| Pattern | `section.title` | `question.text` |
|---|---|---|
| Letter prefix `A.` `B.` `C.` | **0** | **8** |
| Number prefix `1.` `2.` | 13 | 0 |
| Starts `Element N:` | 6 | 0 |

Letter prefixes are used *exclusively* for questions. But the prompt said:

> `section.title`: … **Often starts with a letter prefix (A., B., C.)**

— the exact opposite, while `question.text` said nothing about letter prefixes despite its
own example being `"A. Types and amount of scientific data…"`. The description contradicted
its own example, and the models followed the description.

### Fix

`section.title` now states it does **not** include lettered sub-items; `question.text`
states it frequently is one.

### Result — split by model

| | Path A before → after | `question.text` F1 | Lettered items mislabelled |
|---|---|---|---|
| gemma4:e4b | 67.6% → **74.3%** (+6.7) | 16.2% → **41.9%** | 5/8 → **0/8** |
| llama3.1:8b | 61.7% → 61.9% (+0.2) | 4.1% → 4.2% | 7/8 → **7/8** |

The fix works completely on gemma4 and **not at all** on llama3.1:8b, which still
mislabels 7 of 8 lettered items. The instruction is in the prompt; the 8B model does not
act on it. Negative constraints ("does NOT include…") appear to need more capability than
positive ones.

`section.title` improved alongside `question.text` on gemma4 (70.5% → 81.3%) because it
stopped absorbing items that were never section titles.

### This also explains an earlier unknown

On 5 August I recorded an unexplained −16pp on pdfplumber when the duplicated prompt was
removed. The deleted second copy contained exactly this guidance
(*"Does NOT include sub-items labelled A., B., C."*). Removing it lost the correction.
**That open question is now answered.**

## 5. 70B run — CPU offload

The first attempt loaded at **15% CPU / 85% GPU** and had not finished one sample in 12
minutes (previously 5.5 min/sample fully on GPU).

**Cause:** a stale `llama-server` (PID 26876) from the earlier Vulkan-era session was still
holding ~12 GB on all four GPUs, leaving only ~46 GB for a model needing ~54 GB.

**Fix:** killed all `llama-server` processes, restarted Ollama with all four GPUs visible
(`CUDA_VISIBLE_DEVICES=0,1,2,3 OLLAMA_VULKAN=0 OLLAMA_SCHED_SPREAD=0`). Model then loaded
at **100% GPU**, ~13 GB per card, and averaged 132 s/sample.

**Check before any long 70B run:** `ollama ps` must show `100% GPU`. Anything less means
CPU offload and a multi-hour run.

## 8. Verified the F1 calculation independently

Prompted by a question about whether scoring was correct, every figure was recomputed from
the raw match records and compared against what the code produces.

| | TP | Predicted | Gold | Precision | Recall | F1 |
|---|---|---|---|---|---|---|
| Path A | 96 | 179 | 132 | 53.63% | 72.73% | 61.74% |
| Path B | 97 | 181 | 134 | 53.59% | 72.39% | 61.59% |

Independent recomputation matched to 9 decimal places on both paths, and both accounting
identities hold exactly:

```
gold = TP + wrong-label + missed        96 + 25 + 11 = 132
pred = TP + wrong-label + spurious      96 + 25 + 58 = 179
```

The second identity is the one that matters: it confirms the 58 spurious items — produced
with no counterpart in the reference — are counted against precision. A metric that quietly
dropped them would look considerably better than it should.

Per-label F1 uses a separate code path and was checked too; all five labels agree exactly,
and support sums to 132.

**Conclusion: the scoring is correct.** No change needed.

## 9. Blocks versus items — a real source of confusion

A manual check of sample 1 counted 12 mislabelled blocks for llama3.1:8b. The scoring
reports 9 wrong items plus 4 spurious. Both are right; they count different things.

Scoring happens *after* `converter.to_structured()`, which merges consecutive blocks sharing
a label. The consequence is that a block error costs a different amount depending on which
label was wrong:

| Blocks | Mistake | Cost |
|---|---|---|
| 31–35, five consecutive | `answer.text` -> `question.text` | merge into **one** item |
| 5, 12, 20, 22, 24, 29, 38 | `question.text` -> `section.title` | stay **seven separate** items |

Every `section.title` opens a new section, so those can never merge. Five block errors cost
roughly one item; seven cost seven.

**Practical guidance:** compare a manual count against *wrong-label + spurious*, not against
the block count. For sample 1 that is 13, against the manual 12.

This is now explained inside each results notebook rather than living only in conversation.
