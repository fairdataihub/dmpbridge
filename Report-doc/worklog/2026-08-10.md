## 1. Path B was deleting the thing it exists to measure

### The collision

Two rules, each defensible alone.

**The annotation rules** fill a blank question from its section heading:

```
heading:  "B. Scientific data that will be preserved and shared"
question: ""                       <- blank
          -> rule fills it ->
question: "B. Scientific data that will be preserved and shared"
```

**The scorer** carried a dedup guard in `extract_gold()`:

```python
if q_text and q_text != sec_title:      # skip the duplicate
```

The rule makes the question *equal* to the heading. The guard then discards
anything equal to the heading. Every question the rules repaired was deleted
before it could be scored.

The guard applies to the prediction as well as the annotation —
`_match_structured()` line 137 parses the prediction with the same function — so
it fired on **both sides** of the comparison.

### Scale

| | items | discarded by the guard |
|---|---|---|
| questions the rules add | 44 | **42** |
| questions in the new annotation | 56 | **38** |

Path B was scoring 18 questions against an annotation containing 56, and
crediting 2 correct where the real figure is 26.

### Why it survived this long

Path A is unaffected: the **old** annotation contains **0** questions that repeat
their section title, so the guard never touches old gold — it only trims the
prediction, which is what it was written for. The new annotation is *built* on
that repetition. One line, correct for one path, silently inherited by a second
path it defeats.

It was also invisible in the headline: micro F1 moved by 0.002. The tell was in
the support column — 18 where the annotation has 56.

### Fix

`extract_gold()` now takes `dedup_question_title`, default `True`. Path A keeps
it; **Path B passes `False` on both sides**. Applied in `load_method_new()`,
`run_single()`, and the explorer notebook's `score_path()`.

### Results

Path A is unchanged, which is the check that the fix is scoped correctly:

| model | Path A before | Path A after |
|---|---|---|
| llama3.1:8b | 0.623 | 0.623 |
| gemma4:e4b | 0.703 | 0.703 |
| llama3.3:70b | 0.754 | 0.754 |

Path B, and the label that actually moved:

| model | Path B f1 | `question.text` f1 | support |
|---|---|---|---|
| llama3.1:8b | 0.621 -> 0.617 | **0.077 -> 0.409** | 18 -> 56 |
| gemma4:e4b | 0.700 -> 0.707 | ~0.10 -> **0.610** | 18 -> 56 |
| llama3.3:70b | 0.755 -> 0.740 | ~0.11 -> **0.632** | 18 -> 56 |

True positives on Path B rise 96 -> 120, 109 -> 130, 108 -> 134.

## 2. What this changes in the conclusions

Previous sessions recorded that Path A and Path B are near-identical and
concluded the rules do almost nothing. **That was an artefact of the guard.**

The rules are in fact the largest single improvement anywhere in this project:

| model | `question.text` Path A -> Path B |
|---|---|
| llama3.1:8b | 0.047 -> 0.409  (+0.363) |
| gemma4:e4b | 0.419 -> 0.610  (+0.192) |
| llama3.3:70b | 0.500 -> 0.632  (+0.132) |

Every other label is **+0.000 exactly** on all three models. The rules only ever
write to `question.text`, so that is the expected signature — and it is now
asserted by a test rather than observed and hoped for.

They help most where the model is worst, which is what a floor should do.

### The headline F1 must not be compared across paths

Path A scores **132** items, Path B **172** — the revised annotation carries 40
more questions. So Path B answers a bigger question, and a lower number there
does not mean a worse pipeline. On the 40 extra items the models score roughly
46–66%, below their own average, which dilutes the micro figure while adding real
value.

`items scored` is now printed as the first row of section 1 in every results
notebook, with a warning beneath it that appears only when the two supports
differ.

A test never seen to fail is not yet evidence.

The accounting identity is the one worth keeping: if a spurious item were quietly
dropped rather than counted against precision, `TP+FP = predicted` breaks and the
score would look better than it is.

### `notebooks/4-pipeline-explorer.ipynb` — new

One settings cell (`SAMPLE` / `PDF_PATH`, `MODEL`, `EXTRACTOR`, `RERUN`,
`SHOW_MERGE`), then every stage shows its real output as a styled DataFrame with
a note on what it did and what goes wrong there. Works on the 10 samples or on
any PDF; scoring appears only when an annotation exists. Reuses saved output by
default, so it opens instantly.

Colour encodes meaning rather than decorating: one fixed tint per label reused in
every table, red for empty fields, green for rule-filled ones, and a diverging
scale on the mistakes `change` column.

Also new: `scripts/inspect_sample.py` — same thing from the command line.

### Line merging verified lossless

`data/output/1_extracted/pdfplumber_unmerged/` (gitignored) now holds the raw
line-level extraction beside the merged version. Across all 10 samples,
**merges == characters added**, exactly — 34/34, 128/128, 68/68 — and the text is
byte-identical once whitespace is stripped. Every join inserts one space and
nothing else.

`merge_wrapped_lines()` is a pure function on a block list, so it can be applied
to saved raw JSON after the fact; doing so reproduces the pipeline's own output
byte-for-byte. Useful for tuning the merge rule without re-reading any PDF.

### Two stage-1 defects found, neither fixed

**Underlined headings are invisible.** An underline is a drawn rectangle, not a
font attribute, so the reader never sees it and the heading stays fused to the
answer beside it — one block, one label, so one of the two is always wrong.
Sample 6 uses underlined headings throughout: **all five of its section titles
score as never produced**, capping the document near 0.55. gemma4:e4b and
llama3.3:70b both scored exactly 0.522, which is the signature of a stage-1
ceiling rather than a model difference.

A prototype (detect thin horizontal rects, split the line at the end of the
underlined span, then merge) gave, on sample 6 alone:

| model | before | prototype |
|---|---|---|
| gemma4:e4b | 0.522 | 0.720 |
| llama3.3:70b | 0.522 | **0.957** (TP 6->11, FP 6->1, FN 5->0) |

Geometry note: the rule sits ~1.4pt **above** the block's `bottom`, because that
edge includes descender space. A −3…+5pt window works.

**Hanging indents block valid merges.** `_same_column` uses a 2.0pt tolerance, so
a continuation line indented 18pt under a numbered heading fails, even when every
other cue fires. 8 merges corpus-wide: 5 in sample 6, 2 in sample 5, 1 in
sample 2.

Neither is implemented. Both change stage 1 for every model, so they need the
same discipline as a prompt change — run all 10, re-run all three models, compare
against the noise floor. Fix and measure them separately or the effects confound.
