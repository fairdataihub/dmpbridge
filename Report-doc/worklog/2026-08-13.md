## 1. Docling extractor, take three — whole-section grouping

Adopted a user-supplied `test_docling.py` almost verbatim rather than
extending yesterday's item-tree+regex version: OCR in Docling's auto mode
(`do_ocr=True`, no forcing), whole-document markdown export, split into
sections at each heading line. Chosen deliberately over finer-grained
splitting, with the trade-off stated up front and accepted: a section
becomes exactly **one heading block + one body block**, so a section
containing both a question and its answer can only get one label. This is
not the extractor from earlier this week or yesterday — it is a third,
separate design.

### Two real bugs found in the port, both by testing output rather than reading code

- **Markdown markers claimed preserved, actually stripped.** The ported
  `split_into_sections()` does `heading.lstrip("#")` before storing the
  heading text — so `text` fields were plain strings, not markdown, despite
  the module doing exactly what a version from yesterday was fixed to
  avoid. Caught by the user asking "why is the output not markdown", not by
  inspection. Fixed by keeping the `#`/`##`-prefixed line as `text` and
  using the stripped version only for the internal `section` grouping key.
- **OCR configured but never actually exercised.** `do_ocr=True` loads the
  RapidOCR engine on every run (visible in logs) but Docling's auto mode
  only fires it on pages without a usable text layer — none of the 10
  sample PDFs are scanned, so OCR never actually ran on real text. Verified
  by checking for the known OCR misread from a forced-OCR run two days ago
  (`"iii"` → `"ili"`): absent here, meaning the native text layer is what's
  actually being read, not OCR output. This is disclosed as an open gap,
  not fixed — the project still has no evidence of what OCR does on a
  document that actually needs it.

### Two text-quality bugs, found by inspecting real block content

- OCR-reconstructed spacing produced runs of 2+ spaces mid-word/mid-sentence
  (`"Types  of  data"`). Fixed with a regex collapsing 2+ horizontal
  whitespace to one, applied per line so it cannot touch the single
  newlines the module relies on to keep list items separate.
- `export_to_markdown()` defaults to `escape_html=True`, so a literal `>`
  in source text came through as `&gt;`. Fixed by passing
  `escape_html=False` — this text goes to an LLM prompt, not a browser.

### First real scores for this design

Ran `llama3.1:8b` and `gemma4:e4b` end to end (10 samples each, extraction
cached and reused between runs). Scored at the project's 100% overlap
default unless noted:

| model | extractor / design | Path A f1 | Path B f1 |
|---|---|---|---|
| llama3.1:8b | pdfplumber (baseline) | 0.287 | 0.313 |
| llama3.1:8b | docling, item-tree (yesterday, reverted) | 0.359 | 0.339 |
| llama3.1:8b | docling, whole-section (today) | **0.600** | **0.627** |
| gemma4:e4b | pdfplumber (baseline) | 0.656 | 0.665 |
| gemma4:e4b | docling, item-tree (yesterday, reverted) | 0.438 | 0.415 |
| gemma4:e4b | docling, whole-section (today) | **0.689** | **0.701** |

**This resolves an open question from yesterday's worklog.** Yesterday,
`gemma4:e4b` regressed on docling relative to pdfplumber while
`llama3.1:8b` improved, and nothing explained why. Today, with the
whole-section design, *both* models score above their pdfplumber baseline
— the earlier gemma4 regression looks specific to the item-tree design
(most likely its fragmentation/false-positive behaviour, not something
inherent to Docling), though this was not directly re-tested today and
should be treated as a plausible explanation, not a confirmed one.

Also re-scored both models at 75% overlap for direct comparison against

0.670/0.673, gemma4:e4b 0.740/0.733 — same pattern, every score higher at
the looser threshold, ranking unchanged, consistent with the

`6-threshold-comparison.ipynb`.

### A defect that reached the final document, not just the score

The markdown markers kept in block text (the fix above) leaked all the way
through `to_structured()` into the actual document: a stage-3 `title` field
literally read `"## Data Management Plan:"`. Checked whether this affected
any score already reported — it does not, because `tokenize()` strips
non-alphanumeric characters before matching, so `"## Data Management
Plan:"` and `"Data Management Plan:"` produce identical token sets.
Confirmed this directly rather than assuming it. Fixed anyway, since the
structured/final JSON is meant to be the real, readable document: added
`_strip_markdown()` in `converter.py`, applied once at the single point
every block's text enters the structuring walk. Regenerated stage 3 and 4
for both models directly from the already-labeled stage-2 JSON (no
Ollama re-run needed) and verified **0 of 40** structured/final files still
contain a marker, with scores unchanged at the values above.

## 2. The evaluation pipeline: Path A/B unified, and a real gap closed

Prompted by wanting a config that "covers all options" — this led to
inspecting how Path A and Path B actually work, not just how they're used.

### What was found

`load_method()` (evaluate.py) and `load_method_new()`
(annotation_rules.py) were two ~80-line, independently maintained
functions doing the same scoring loop against different directories and
a different `dedup_question_title` setting. They had already diverged
once for real — the 2026-08-10 bug where Path B's dedup guard silently
deleted 42 of 44 rule-added questions came directly from this duplication.
Separately, `Experiment.evaluate()` (the YAML-driven entry point) called
`load_method` only — **Path B was not reachable from a config-driven run
at all**, and tracing why revealed it was worse than "not called":
`Experiment._run_combination()` wrote stage 3 to a bespoke
`out_dir/<tag>/sample{i}_structured.json` layout that nothing else in the
project reads, and never wrote stage 4 at all. Running an experiment via
YAML and then trying to evaluate Path B from it would have found nothing
to score, silently.

### What was built

- **`EvaluationPath`** (dataclass, `evaluate.py`) — `name`, `predicted_dir`,
  `annotation_dir`, `dedup_question_title`, `threshold`. `from_dict`/`to_dict`
  for YAML round-tripping.
- **`evaluate_path(tag, path, exclude=None)`** — the one scoring loop,
  replacing both duplicated versions. Driven from the annotation side (a
  sample with no prediction is skipped with a warning, not an exception) —
  chosen over the old Path-B behaviour of driving from the predicted side,
  which would raise if an annotation were missing.
- **`PATH_A`, `PATH_B`** — the project's two paths as data.
  `load_method()`/`load_method_new()` kept as thin wrappers so every
  existing caller (8+ sites across notebooks and scripts) needed zero
  changes.
- **`ExperimentConfig.evaluation`** — an optional list of path dicts in the
  YAML; empty/absent resolves to `[PATH_A, PATH_B]`, so all three existing
  `experiments/*.yaml` files still load and behave identically with no
  edits.
- **`Experiment._run_combination()` rewritten** to write stage 2/3/4 to the
  same `data/output/{2,3,4}_*/​<tag>/` layout `dmpbridge-wholedoc` and every
  notebook already use, and to actually pass `final_path` to
  `run_and_save()` so stage 4 gets produced. This is the fix that makes
  Path B reachable from a YAML-driven run for the first time.
- **`Experiment.evaluate()`/`summary()` rewritten** to iterate
  `config.evaluation_paths`, returning
  `{model: {extractor: {path_name: (df, conf, errors)}}}` instead of the
  old two-level dict with Path A hardcoded in.

### Verification, not assumption

- Captured `micro_prf1()` output for 5 tags (3 pdfplumber models + 2
  docling models) × 3 thresholds (default, 0.75, 1.0) × both paths = 30
  combinations, using the pre-refactor code (via `git stash`). Re-ran the
  identical 30 combinations post-refactor. **0 mismatches.**
- Full test suite: one real failure surfaced
  (`test_load_method_scores_final_json_against_resolved_gold`) — it
  monkeypatched the old per-sample `resolve_new_gt_path()` function, which
  the new architecture correctly no longer calls at all (it lists the
  annotation directory instead). Not a weakened test: updated to monkeypatch
  `PATH_B.annotation_dir`/`predicted_dir` directly, which required overriding
  *both* fields — `predicted_dir` had already been snapshotted from the
  real `FINAL_DIR` at import time, so patching the module-level `FINAL_DIR`
  name alone (what the original test did) does not retroactively affect it.
  118/118 passing after the fix.
- Loaded the new `experiments/full-example.yaml` (3 models × 2 extractors ×
  2 paths, fully commented, every option in one file) through the real
  `Experiment.evaluate()` and got 12 results: 10 real, matching every
  number already established this session, and 2 (`llama3.3:70b` +
  `docling`, genuinely never run) reported as "no data" rather than
  crashing — the direct, working demonstration of graceful missing-data
  handling this redesign was meant to provide.
