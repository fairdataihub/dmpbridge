## 2. pdfplumber line merging — the day's main result

### The problem

pdfplumber segments by line, not paragraph, so one answer arrived as several blocks.
The classifier labels each independently and is mostly consistent (only 13 of 432
mid-sentence breaks got an inconsistent label), but short trailing fragments —
`"published manuscripts."`, `"and double checking work."` — are easy to mislabel alone.

**One mislabelled fragment costs twice.** The converter only merges neighbours that
already share a label, so the fragment cannot be reabsorbed: it becomes a spurious item
(false positive) *and* its parent paragraph loses its ending, which can push the parent
below the 0.75 containment threshold and lose it too (false negative).

### The fix

New `dmpbridge/preprocess/line_merger.py`, wired into `PdfplumberExtractor` behind
`merge_lines` (default `True`). Joins two lines when a continuation cue is present —
next line opens lowercase, or this line looks unfinished *and* reaches the right margin —
and page, font, weight and left edge all agree.

**The decisive signal is the right margin, not punctuation.** A wrapped line runs out to
the edge of the text column; a heading stops well short of it. Wrapped lines here end
within ~35pt of the margin, headings 300pt+ short. Without that test every heading reads
as "unfinished" (headings rarely end in a full stop) and gets welded onto the text below.
An early version did exactly that, joining a document title to the section title beneath it.

### Result — controlled A/B, both arms back to back

llama3.1:8b, all 10 samples, current rules:

| | Path A F1 | Path B F1 |
|---|---|---|
| No merging | 34.9% | 35.4% |
| **With merging** | **63.4%** | **56.5%** |
| | **+28.4** | **+21.1** |

Precision +32.3pp (24.7% → 57.0%) — exactly where the mechanism predicted.
Per label (Path B): `section.description` +33.0, `answer.text` +31.5, `section.title` +12.2,
`question.text` +2.2, `title` −10.0 (on 10 gold items, so one document).

Also ~2× faster: 71s vs 168s, since the model sees 251 blocks instead of 735.

**Does not change the extractor ranking** — merged pdfplumber is still expected to sit
below docling and lighton.

## 3. Annotation rules — replaced with the `Rules.xlsx` truth table

Old behaviour (fill empty `question.text` from section title, or document title) replaced
by the 16-row spreadsheet. All sixteen rows collapse to four branches:

| Situation | Action |
|---|---|
| q.text empty, sec.title empty, title present | title → question.text *(rows 9, 10)* |
| q.text empty, sec.title empty, only description | description → both *(row 2)* |
| q.text empty, sec.title present | sec.title → question.text *(rows 3, 4, 11, 12)* |
| q.text present, sec.title empty | question.text → sec.title *(rows 5, 6, 13, 14)* |
| both present, or nothing to copy | leave *(rows 1, 7, 8, 15, 16)* |

**Validation: 9 of 10 documents match the reference files exactly.** Sample 5 is the
exception — it needs 11 questions merged into 6 with answers joined, which no row covers.

### Three issues found in the spreadsheet, all since corrected

1. **Rows 9/10 contradicted the reference data** — said to fill `section.title` as well as
   `question.text`, but samples 4 and 7 leave `section.title` empty. Corrected to
   question.text only, which took matching from 7/10 to 9/10.
2. **Row 12** said `"question.title"` — no such field. Corrected to `question.text`.
3. **Row 11** had a stray doubled quote. Cosmetic.

### Separately: Rule 3 title-clearing removed

The reference files `sample4_dmp_new.json` and `sample7_dmp_new.json` were revised to
**keep** the document title after it is copied into a question; the rule was still clearing
it. Verified across all ten files — every one retains its title — and removed the clearing step.

**Note for future runs:** rows 5/6/13/14 (copy `question.text` → `section.title`) are new
behaviour, and interact with scoring. `extract_gold()` drops a `question.text` that equals
its section title to avoid double-counting, so filling `section.title` from `question.text`
effectively relabels the item. This is the likeliest reason Path B now scores *below* Path A
on pdfplumber (56.5% vs 63.4%), where previously Path B usually helped. **Worth
investigating before running the remaining eight configurations.**

## 5. Four-stage output layout

```
data/output/
├── 1_extracted/<extractor>/sampleN.json     text blocks, no labels
├── 2_labeled/<tag>/sampleN.json             blocks + label + confidence
├── 3_structured/<tag>/sampleN.json          DMP Tool schema      ← Path A scores this
└── 4_final/<tag>/sampleN.json               Rules.xlsx applied   ← Path B scores this
```

Filenames identical at every stage, so one document can be followed folder to folder.

**Stage 1 is keyed by extractor and cached.** Extraction doesn't depend on the model, so
labeling a corpus with three models costs one extraction, not three — several minutes per
sweep with lighton, which runs a vision model over every page. Verified: a second model
reported *"reusing 44 cached block(s)"* and did no extraction.

**Stages 3 and 4 are now genuinely separate.** Previously `--apply-rules` overwrote stage 3
in place, so the converted and unconverted forms could never both exist.

CLI changes: `--apply-rules` replaced by `--no-rules` (stage 4 is written by default);
`--no-cache` added.
